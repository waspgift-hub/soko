--------------------------------------------------------------------------------
  1.1 VISION & MARKET CONTEXT
--------------------------------------------------------------------------------

  Soko Vibe ("Soko Langu") is a Tanzania-first multi-vendor e-commerce
  marketplace. It replaces informal WhatsApp/Instagram commerce with a
  trust-guaranteed transaction layer: escrow-held payments, KYC-verified
  sellers, and real-time buyer-seller communication. No live-streaming,
  no ride-hailing, no mandatory buyer subscription - revenue is strictly
  transactional.

  Target geography: Tanzania (26 regions, all districts selectable at
  checkout). Language: Swahili (primary), English, Chinese (zh). Currency:
  TZS stored canonically; 9 display currencies via ExchangeRateService.

  Platform primitives:
    - Product listing with variant/wholesale support
    - Search + Discovery (For You / Nearby / Trending)
    - Buyer Requests (reverse marketplace: buyer posts need, sellers bid)
    - Pay-to-Boost (sponsored placement)
    - Escrow checkout with OTP handover
    - In-app chat + WhatsApp deep-link fallback
    - Flash sales & price-drop broadcasts

--------------------------------------------------------------------------------
  1.2 CORE BUSINESS MODEL
--------------------------------------------------------------------------------

  +----------------------------+-----------------------------------------------+
  | Revenue Stream             | Mechanism                                     |
  +----------------------------+-----------------------------------------------+
  | Platform Commission        | 3.5% of productPrice on every completed       |
  |                            escrow release. Recorded in                    |
  |                            revenue_transactions (type: commission).       |
  +----------------------------+-----------------------------------------------+
  | Pay-to-Boost (Ads)         | 3 tiers: Bronze 1,500 TZS/3d, Silver 3,000  |
  |                            TZS/7d, Gold 10,000 TZS/30d. Product gets     |
  |                            isBoosted=true + boostExpiresAt. Recorded     |
  |                            as revenue_transactions (type: boost).         |
  +----------------------------+-----------------------------------------------+
  | AdMob Monetization         | Banner + Interstitial (20m cooldown) +        |
  |                            Rewarded gates. Ad views -> ad_views docs.    |
  |                            Estimated 15 TZS/view; actual via AdMob console|
  +----------------------------+-----------------------------------------------+
  | Payout Fees (pass-through) | 2,000 TZS flat deducted from seller on        |
  |                            withdrawal + ClickPesa tiered payout fees      |
  |                            absorbed in sellerReceives calculation.        |
  +----------------------------+-----------------------------------------------+
  | Collection Fees            | 180 TZS Mongike legacy OR ClickPesa tiered   |
  |                            (54-7,960 TZS) - platform absorbs; shown as   |
  |                            "Bure" (Free) at checkout.                    |
  +----------------------------+-----------------------------------------------+

  Explicitly EXCLUDED from business model (out of scope):
    - Live-stream selling (no WebRTC/RTMP)
    - Ride-hailing / logistics fleet (seller arranges bus/bodaboda; proof only)
    - Buyer subscription paywall (all buyer features free)

  Request flow (soko_langu/lib/services/api_config.dart + server/src/app.js):

    App Service (e.g., MongikeService / ClickPesaService)
      -> HTTP POST https://api.sokovibe.co.tz/api/...  (Worker cache check)
           -> Render origin (Express)
              -> rateLimiter -> authMiddleware (Firebase verifyIdToken)
              -> Firestore / Redis / external provider
              -> JSON response + auditLog
      <- UI via setState / Provider.notifyListeners() / StreamBuilder

  Webhook flow (ClickPesa -> Backend):

    ClickPesa -> POST /api/clickpesa/webhook
                  header x-webhook-secret, IP allowlist, checksum
                  -> verifyWebhook middleware (403 on mismatch)
                  -> Redis SETNX idempotency lock
                  -> Firestore transaction (status + balances + revenue)
                  -> OneSignal + Meseji + in-app notification
                  -> 200 OK

  Listener process (server/listener.js - optional sidecar):

    Firestore onSnapshot (transactions, messages, products)
      -> in-memory dedup Map/Set
      -> FCM + SMS fan-out (supplements webhook notifications)

--------------------------------------------------------------------------------

             |                                   |

             v                                   v
  +---------------------+              +----------------------+

  | - ClickPesaService  | ------------->| - ProductRepository  |
  | - OrderApi          |  Firestore/  | - ChatRepository     |
  | - WalletApi         |  HTTP        | - UserService        |
  | - GroqService       |              +----------------------+
  +----------+----------+                       |
             |                                 | Hive cache
             v                                 v
  +---------------------+              +----------------------+
  | Backend / Firestore |              | LocalCacheService    |

  | - Firestore SDK     |              +----------------------+

  Why this split:
    - App NEVER calls ClickPesa/Meseji/Groq directly; all proxied via
      backend (keeps secrets server-side, allows fee logic centralization).
    - Product reads are client-direct to Firestore (realtime, offline-first).
    - Financial writes are server-only (admin SDK bypasses rules).

  No Bloc/Riverpod - intentional simplicity; Provider covers 95% cases.
  Future migration path: Riverpod if provider count exceeds 10+.

  Example - AuthNotifier skeleton (lib/notifiers/auth_notifier.dart):

    class AuthNotifier extends ChangeNotifier {
      AuthStatus _status = AuthStatus.loading;
      User? _user;
      bool _isAdmin = false;

      Future<void> initialize() async {
        _user = FirebaseAuth.instance.currentUser;
        if (_user != null) {
          final doc = await FirebaseFirestore.instance
              .collection('users').doc(_user!.uid).get();
          _isAdmin = doc.data()?['isAdmin'] == true;
          _status = AuthStatus.authenticated;
        } else {
          _status = AuthStatus.unauthenticated;
        }
        notifyListeners();
      }
      // login/register/OTP -> Firebase + Firestore users/{uid} doc
    }

  ORDER STATE MACHINE (server/orders.js ORDER_STATUS):

    pending
      -> awaiting_shipping_quote  [after POST /api/orders/create mirror]
        -> quoted                [seller sets shipping via POST /api/orders/transition]
          -> paid / paid_escrow_hold / escrow_hold  [webhook confirms payment]
            -> dispatched        [seller POST /api/escrow/dispatch with proof]
              -> delivered       [buyer confirms arrival]
                -> delivery_confirmed -> completed [POST /api/escrow/release, funds move]
              -> disputed        [POST /api/escrow/dispute -> admin resolve]
              -> cancelled/refunded [buyer cancel before dispatch -> payout refund]
            -> failed            [payment failed, retry via /api/retry-payment]
          -> awaiting_shipping_quote (loop if quote rejected)
      -> failed (immediate if validation fails)

  Escrow sub-states: escrow_hold holds pendingEscrow (locked); completed moves
  to sellerBalance (available). Auto-release sweeps escrow_hold where
  escrowExpiresAt <= now (60 min interval + external cron).

  Related: revenue_transactions/{id} (commission/boost/refund legs),
           payouts/{id}, withdrawals/{id}, admin_withdrawals/{id},
           audit_log/{id}, deposits/{depositRef}

--------------------------------------------------------------------------------
  4.3 ESCROW WORKFLOW ARCHITECTURE
--------------------------------------------------------------------------------

  Escrow is the trust primitive: buyer funds are HELD server-side until OTP
  delivery confirmation, then atomically released to sellerBalance.

  States: pending -> escrow_hold -> dispatched -> delivered -> completed
                    \-> disputed (admin)  \-> cancelled (pre-dispatch)
                    \-> failed

  ASCII Sequence - Happy Path:

  Buyer         App (Flutter)         Backend (Express)       ClickPesa    Seller App
   |                |                        |                  |              |
   | Buy Now        |                        |                  |              |
   +--------------->| POST /api/orders/create|                  |              |
   |                +----------------------->| Firestore orders  |              |
   |                |  transactions pending | awaiting_shipping |              |
   |                |<-----------------------+                  |              |
   |                |                        |  notify seller   |              |
   |                |                        +------------------------------->|
   |                |                        |                  |              |
   |                |  (seller quotes)       | POST /api/orders/transition    |
   |                |                        | quoted + shippingCost          |
   |   "Lipa Sasa"  |  POST /create-marketplace-payment-link (Bearer, 5/60s)  |
   +--------------->|  + amount calc (processingFee)                           |
   |                +----------------------->| validate (suspended, duplicate,|
   |  PaymentBanner |                        |  daily limit 5M)               |
   |  "Check phone" |                        |  transactions pending          |
   |                |                        |  clickpesaCollect(phone)       |
   |                |                        +----------------->| USSD Push    |
   |  Enter PIN     |                        |                  |----->|       |
   |  on phone      |                        |                  | PIN ok       |
   |                |                        |<-----------------+             |

  Code - Escrow Release (server/src/modules/escrow/ - simplified):

    // POST /api/escrow/release  {orderId, userId}  (Buyer, dispatched only)
    const tx = await db.runTransaction(async (t) => {
      const orderSnap = await t.get(ordersRef.doc(orderId));
      if (orderSnap.data().status !== 'dispatched') throw new Error('INVALID_STATE');
      if (orderSnap.data().buyerId !== userId) throw new Error('FORBIDDEN');
      // atomic ledger move
      t.update(usersRef.doc(sellerId), {
        pendingEscrow: FieldValue.increment(-sellerReceives),
        sellerBalance: FieldValue.increment(sellerReceives),
        grossSalesVolume: FieldValue.increment(sellerReceives),
        totalSales: FieldValue.increment(1)
      });
      t.update(ordersRef.doc(orderId), { status: 'completed', completedAt: now });
      t.update(transactionsRef.doc(orderId), { status: 'completed', escrowReleased: true });
      t.set(revenueRef.doc(), { type: 'commission', amount: platformFee, orderId });
      t.set(auditLogRef.doc(), { action: 'escrow_release', orderId, actor: userId, at: now });
    });
    // after tx: sendOneSignal + sendSms (localized via notif_lang)

  Code - ClickPesa webhook guard (server/clickpesa.js / src/modules/payments/):

    router.post('/api/clickpesa/webhook', async (req, res) => {
      if (!verifyIp(req.ip)) return res.status(403).send('IP not allowed');
      if (!verifyChecksum(req.body)) return res.status(403).send('bad checksum');
      // Redis SETNX double-spend lock
      const lock = await redis.set(`webhook:${txnId}`, '1', 'NX', 'EX', 3600);
      if (!lock) return res.status(200).send('already processed');
      // ... Firestore status update + notifications
      res.status(200).send('ok');
    });

  Holding periods:
    ESCROW_AUTO_RELEASE_DAYS env default 14 days
    Local delivery constant 3 days (internal), regional 7 days (separate)
    Admin force: POST /api/escrow/admin-release (x-admin-secret)
    Retry failed payout: POST /api/escrow/retry-payout

  Auto-release (two mechanisms):

    a) Internal setInterval every 60 min (first run 60s after boot):
         query transactions where (status==escrow_hold OR dispatched)
               AND escrowExpiresAt <= now
         -> for each: status completed, sellerBalance += sellerReceives,
            notify buyer "Escrow Imetolewa Kiotomatiki", seller "Malipo Yamekamilika"

    b) External cron endpoints:
         POST /api/release-expired-escrows (Bearer+isAdmin)
         POST /api/cron/release-escrows (x-cron-secret = ADMIN_SECRET)
         -> for cron-job.org / GitHub Actions hourly

--------------------------------------------------------------------------------
  4.4 REFUND & DISPUTE RESOLUTION WORKFLOWS
--------------------------------------------------------------------------------

  [CANCEL] Before dispatch (buyer, escrow_hold):

    POST /api/escrow/cancel {orderId, userId}
      Validate: status escrow_hold, caller is buyer
      Action: mongikePayout/clickpesaPayout REFUND productPrice - PAYOUT_FEE 2000
              to buyer phone; seller pendingEscrow decremented; status cancelled
              (or refunded)
      Notify: FCM+SMS both parties
      Audit: audit_log refund entry

  [DISPUTE] After dispatch but before confirm:

    POST /api/escrow/dispute {orderId, userId, reason, evidenceUrls}
      -> status disputed, funds stay held (pendingEscrow untouched)
      -> FCM to seller + all admins (admin_notifications)
      Evidence: disputeEvidence subcollection (planned) or evidenceUrls array

    Admin resolution:

      POST /api/escrow/admin-resolve-dispute {orderId, resolution} (admin)
        resolution 'release' -> status completed, sellerBalance += (funds to seller)
        resolution 'refund'  -> clickpesaPayout productPrice to buyer
                               + penalties to seller (revenue reversal)
                               + status refunded, pendingEscrow decremented
        SLA: FINANCE_DISPUTE_SLA_HOURS 72 (finance-runner monitor)

  [FAILED] Payment failed path:

    Webhook sets status failed; ussdFailed=true, ussdError string
    Client RealtimePaymentBanner shows FAILED instantly (no infinite loading)
    Buyer may retry: POST /api/retry-payment {orderId} (stale pending boosts
    also swept via cron every 60 min -> mark failed).

  Idempotency: every financial mutation uses Firestore atomic transaction +
               Redis lock + unique transactionId to prevent double credit.

--------------------------------------------------------------------------------
  6.1 FIREBASE FIRESTORE SECURITY RULES (firestore.rules:641 lines)
--------------------------------------------------------------------------------

  Version: rules_version = '2'
  Service: cloud.firestore /databases/{database}/documents

  Helpers:

    isSignedIn()     -> request.auth != null
    isOwner(userId)  -> isSignedIn() && request.auth.uid == userId
    isAdmin()        -> isSignedIn() && exists(users/{auth.uid}) &&
                        get(...).data.isAdmin == true
    notSuspended()   -> isSignedIn() && (!exists(...) ||
                        get(...).data.isSuspended != true)

  Field-level guards (critical - prevents client tampering):

    noSensitiveFieldChanges()  // for UPDATE (diff)
      Affects: walletBalance, sellerBalance, pendingEscrow, totalSales,
               grossSalesVolume, totalWithdrawn, isAdmin, isSuspended, kyc,
               isBoosted, boostedUntil, boostTier, createdAt, lastSaleAt,
               lastLoginAt, fcmToken
      Logic: diff(resource).affectedKeys().hasAny(SENSITIVE) -> REJECT
             Exception: single-field fcmToken == null delete allowed (logout)

    noSensitiveCreateFields()  // for CREATE (incoming keys)
      Reject if incoming hasAny {walletBalance, pendingEscrow, totalSales,
        grossSalesVolume, totalWithdrawn, kyc, isBoosted, boostedUntil,
        boostTier, lastSaleAt, lastLoginAt, fcmToken}
             OR sellerBalance !=0 OR isAdmin != false OR isSuspended != false

  Collection rules excerpts:

    /users/{userId}
      read: isSignedIn()
      create: isOwner(userId) && noSensitiveCreateFields()
      update: (isOwner && noSensitiveFieldChanges()) || isAdmin()
      delete: isOwner || isAdmin

    /products/{productId}
      read: true (public catalog)
      create: isSignedIn() && notSuspended() && sellerId==auth.uid
              && !keys.hasAny([isBoosted,boostedUntil,boostTier,
                               isFeatured,featuredUntil,soldCount])
              && rating==0 && reviewCount==0
      update: isSignedIn() && notSuspended() && (
                (sellerId==auth.uid && !diff.hasAny([isBoosted,...isFeatured]))
                || diff.hasOnly([viewCount])          // any user bump views
                || diff.hasOnly([likedBy])             // like/unlike
                || diff.hasOnly([rating,reviewCount])  // review aggregate
                || diff.hasOnly([soldCount])           // server sold
                || isAdmin())
      delete: (sellerId==auth.uid && notSuspended) || isAdmin

    /orders/{orderId}
      read: isSignedIn() && (buyerId==auth.uid || sellerId==auth.uid || isAdmin)
      create: isSignedIn() && buyerId==auth.uid
      update: (buyer==auth.uid && diff.hasOnly([deletedForBuyer]))
              || (seller==auth.uid && diff.hasOnly([deletedForSeller,
                   shippingCost,totalAmount]))  // quote allow
              || isAdmin
      delete: isAdmin
      /delivery_otp/{doc}: read if buyerId==auth.uid; write false (server only)

    /transactions/{txId}
      read/create/update mirrored to orders participant model
      -> client may only soft-delete own row or seller shippingCost
      -> status/money server-owned (webhook/Admin SDK)

    /chat_rooms/{roomId}
      read/create/update: participants.hasAny([auth.uid]) || isAdmin
      messages subcollection: get(parent).data.participants.hasAny([auth.uid])

    /BuyerRequests/{requestId}
      read: isSignedIn() && notSuspended()
      create: buyerUid==auth.uid
      update: isAdmin() || diff.hasOnly([unlockedBy])
      delete: isAdmin()

    /notifications/{notifId}
      read: userId==auth.uid || isAdmin
      create: (userId==auth.uid || isAdmin) && keys.hasAll([title,body,userId])
      update: userId==auth.uid && diff.hasOnly([isRead])
      delete: userId==auth.uid

    /sponsoredCampaigns/{campaignId}
      read: sellerId==auth.uid || isAdmin
      create/update/delete: isAdmin  // server-owned, prevents bid fraud
      /{doc=**} sub: admin only

    Catch-all: match /{document=**} { allow read, write: if false; }
      -> Closed by default; undiscovered collections are denied.

  Indexes enforcement: queries without composite indexes throw
    "index missing" (handled by network_error mapper -> user-friendly SW msg).

  6.2 SECURE API AUTHENTICATION (JWT / Firebase Auth Tokens)

  Middleware (server/src/middleware/auth.js, legacy index.js):

    async function requireAuth(req,res,next) {
      const token = req.headers.authorization?.split('Bearer ')[1];
      if (!token) return res.status(401).json({error:'Missing token'});
      try {
        const decoded = await admin.auth().verifyIdToken(token);
        req.user = decoded; // {uid, email, isAdmin claim?}
        // optional isAdmin check: fetch users/{uid}.isAdmin
        next();
      } catch (e) {
        return res.status(401).json({error:'Invalid token'});
      }
    }

  Admin patterns:
